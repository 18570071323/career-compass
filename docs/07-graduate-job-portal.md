# 07 应届生求职版技术方案（岗位库 + 简历→岗位推荐 + 五维评分 + 校准闭环）

> 项目：ResumeMatch SaaS 新增 **C 端产品线**（应届生求职助手）
> 目标用户：应届毕业生（秋招/春招），在"不知道自己能找什么工作"的起点上，获得
> ① 行业-岗位库 → 简历匹配推荐岗位；② 基于推荐岗位的五维分析报告；③ 持续进化的校准闭环。
> 定位：复用现有 B 端底座（文档解析 / DeepSeek 引擎 / 报告组件 / 多租户），新增独立评分模型与岗位推荐能力。

---

## 1. 与现有系统的关系（复用 vs 新增）

| 能力 | 现状（B 端） | 应届生版（C 端）处理 |
|---|---|---|
| 文档解析 | `doc_extract.py` PDF/DOCX/TXT/图片 | **直接复用**；扩展解析字段（教育/GPA/证书/项目/实习/技能）；支持图片简历与扫描件 PDF（RapidOCR 本地 OCR，见 §23） |
| LLM 解析 | DeepSeek `parse_resume`（json_object） | 复用，prompt 扩展应届生字段 + 证据抽取（动作/工具/量化/角色） |
| 评分 | B 端四维（经验40/技能25/项目20/亮点15，面向社招） | **新增五维模型**（25/25/25/15/10，面向应届），见 §6 |
| 报告 | DeepSeek `generate_report` | 复用，模板按五维 + 补强建议改写 |
| 岗位 | 租户手工维护的 `job`（招聘用） | **新增公开岗位库** `jd_library`（行业-岗位分类树，见 §4） |
| 匹配 | 岗位↔简历双向（挖掘） | **新增 简历→岗位库 推荐流水线**（TF-IDF 粗筛 + 精排，见 §5） |
| 多租户 | 企业租户 | **新增个人租户类型**（tenant_type=personal），复用隔离/配额 |
| 前端 | B 端 5 大页面 | **新增 C 端页面**（上传→推荐→五维报告→反馈）+ B 端校准看板 |
| 校准 | 无 | **新增反馈闭环**（HR 反馈按钮 → 数据回流 → 调参/微调，见 §8） |

> 架构决策：**同一后端、同一底座，C 端是新租户类型 + 新服务模块**，不另起仓库。
> 原因：解析/LLM/报告/文件/配额全复用；B 端 HR 的反馈数据恰好是 C 端校准的数据源，两边天然闭环。

## 2. 总体架构（增量视图）

```

                   │  C端：上传简历 → 推荐岗位列表 → 五维报告(雷达图) → 反馈按钮        │
                   │  B端：报告页增加「校准反馈」入口 + 运营「校准看板」                │
                   └──────────────────────────┬────────────────────────────────────┘
                                              │ REST
                   ┌──────────────────────────▼────────────────────────────────────┐
                   │                        API 层 (FastAPI)                        │
                   │  /candidate/*（上传/推荐/报告/反馈）  /calibration/*（看板/统计） │
                   └──────┬───────────────────────────┬────────────────────────────┘
                          │                           │
              ┌───────────▼───────────┐   ┌───────────▼───────────┐
              │   PostgreSQL          │   │   Redis               │
              │ + jd_library 系列表    │   │ 队列/缓存/限流（复用）   │
              │ + calibration_feedback│   └───────────┬───────────┘
              └───────────┬───────────┘               │
                          │                           │
              ┌───────────▼───────────────────────────▼───────────┐
              │          Celery Worker（复用，新增任务）             │
              │  岗位库清洗入库 | 推荐预筛(本地TF-IDF) | 五维评分     │
              └───────────────────────┬───────────────────────────┘
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        ▼                             ▼                             ▼
  本地解析/切词                  DeepSeek LLM                 岗位库数据源
  pypdf/docx + jieba         解析 / 证据抽取 / 报告          种子数据 → 用户投稿
  TF-IDF 索引(粗筛)            （结构化 JSON 输出）           → 官方API/爬虫(合规评估)
```

**关键设计原则**

1. **零成本预筛 + 有成本精评**：推荐粗筛（TF-IDF）全本地零 LLM 成本；仅对 Top-1~3 岗位做五维评分（一次 LLM 调用抽取全部维度证据）。
2. **确定性规则为主、LLM 只做证据抽取**：五维分数由确定性公式计算，LLM 输出"证据"（结构化 JSON），保证可解释、可回归、可校准；LLM 不直接给分。
3. **评分相对岗位而非绝对能力**：五维评分的目标是"该简历对该岗位的适配度"，由推荐结果决定评分对象。
4. **反馈闭环是一等公民**：分数、证据、权重、档位全部可追溯，HR 反馈落库后按周回流调参。

## 3. 核心流程（数据流）

### 3.1 推荐 + 评分全流程

```
用户上传简历(PDF/DOCX/TXT)
  │ 本地解析（复用 doc_extract）
  ▼
简历纯文本
  │ DeepSeek 解析（应届生版 prompt，json_object）
  ▼
parsed_resume（教育/GPA/证书/实习[]/项目[]/技能[]/自我评价）
  │ ① 硬过滤（学历/城市/技能黑名单）
  │ ② TF-IDF 粗筛：简历全文 × JD 全文 余弦相似度 → Top-30
  │ ③ 精排：结构化字段分(技能覆盖率/教育/赛道) × 0.6 + 相似度 × 0.4 → Top-5~10
  ▼
推荐岗位列表（每岗位含：匹配分、命中技能、缺失技能、匹配理由）
  │ 取 Top-1~3 岗位 → 五维评分
  ▼
五维评分（确定性公式 + LLM 证据抽取，见 §6）
  │ 按权重档位加权 → 总分 + 等级
  ▼
报告生成（DeepSeek，五维诊断 + 差距项 + 补强建议）
  ▼
C 端报告页（雷达图 + 逐维拆解 + 岗位对比） → HR/用户可点「校准反馈」
  ▼
反馈落库 → 周度回流（§8）
```

### 3.2 岗位库维护流程

```
数据源（种子人工 → 用户投稿 → 官方API → 合规爬虫）
  ▼ 归一化清洗（标题标准化、去重、来源标注、质量打分）
  ▼
jd_parsed：LLM 结构化（职责[]/要求[]/技能[]/证书[]/硬性条件）
  ▼ 技能对齐到本体（同义词归并，如 Python≈python≈py）
  ▼
入库 + 生成 TF-IDF 索引/缓存向量 → 可被推荐流水线检索
```

## 4. 行业-岗位库设计

### 4.1 分类树（行业 × 职能 × 细分）

```
行业维度（一级）：互联网/金融/快消/制造/咨询/医疗/能源/教育/传媒/地产 …
职能维度（二级）：技术 / 产品 / 运营 / 市场 / 销售 / 职能(HR/财务/法务) …
细分维度（三级，挂在职能下）：如 技术→前端/后端/算法/测试/运维/数据；金融→投行/行研/固收/风控/量化 …
```

- 分类树同时服务三件事：**岗位归类**、**实习赛道相似度**（经验匹配度子项）、**档位建议**（大厂/国企识别）。
- 实现：`jd_industry` / `jd_category` 两张表，父子引用（`parent_id`），叶子节点挂 JD。

### 4.2 表设计（增量）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `jd_library` | id, source(manual/user_submit/api/crawler), source_url, company, industry_id(FK), category_id(FK), title, city, education(硬性), experience_required, salary_range, jd_text, jd_parsed(jsonb: responsibilities[]/requirements[]/skills[]/certs[]/hard_filters{}), quality_score, is_active, crawl_at, updated_at, tfidf_cache | 公开岗位库，与 B 端 `job`（租户私有）分离 |
| `jd_industry` / `jd_category` | id, parent_id, name, level, type(industry/category) | 分类树 |
| `jd_skill_ontology` | id, canonical_name, aliases(jsonb), skill_class(programming/design/analysis/soft…), is_core_default | 技能本体 + 同义词归并 |
| `cert_scarcity` | id, cert_name, aliases, scarcity_score(1-5), level_hint | 证书稀缺度表（§6.4，初始值待评审） |
| `toolchain_template` | id, category_id(FK), toolchain(jsonb) | 岗位类别典型工具链（技能匹配度子项用） |
| `recommendation` | id, tenant_id, resume_id, jd_id(FK), rank, match_score, hit_skills(jsonb), missing_skills(jsonb), reason(text), status(viewed/applied/ignored), created_at | 推荐记录（用户行为留痕，供校准与后续效果分析） |
| `calibration_feedback` | 见 §8.2 | 反馈闭环 |

> 去重策略：`(source, source_url)` 唯一；人工/投稿按 `(company, title, city)` 相似度合并（编辑距离 + 归一化）。

### 4.3 数据来源与合规

| 优先级 | 来源 | 说明 |
|---|---|---|
| P0 | 人工种子数据 | 首发 50~100 条，覆盖 5 个应届热门类别（技术/产品/运营/市场/职能），人工精选保证质量 |
| P1 | 用户投稿/招聘方共建 | C 端/B 端提供"收录岗位"入口，附 JD 文本 + 来源链接 |
| P2 | 官方开放 API | 有官方开放接口的平台（如部分招聘平台开放 API）优先，天然合规 |
| P3 | 合规爬虫 | **需法务评估平台条款**后实施；只存事实性描述文本并标注来源/抓取时间，控制频率，遵守 robots 与频率限制 |

> 合规底线：标注 `source` + `source_url` + `crawl_at`；收到来源方删除请求即下架（`is_active=false`）；不抓联系方式等个人数据。

## 5. 简历 → 岗位推荐（匹配流水线）

### 5.1 粗筛（本地，零 LLM 成本）

1. **硬过滤**：学历（JD 要求 vs 简历教育）、城市意向（可选）、JD 明确"不要/必须"的关键技能黑名单。
2. **TF-IDF + 余弦**：简历全文与 JD 全文（职责+要求拼接）切词（jieba，加载技能本体词典），`TfidfVectorizer` 余弦相似度，取 Top-30。
   - 为什么先用 TF-IDF：可解释、零依赖、中文岗位文本关键词区分度足够；语义向量（如 bge-small-zh）作为 **M7.4 升级项**（精排替换/融合）。

### 5.2 精排（混合打分）

```
match_score = 0.6 × struct_score + 0.4 × sim_score

struct_score（结构化字段匹配，0-100）：
  技能覆盖率 50%  核心技能命中率（JD 核心技能集合 ∩ 简历技能）/ JD 核心技能集合
  教育匹配   20%  学历 ≥ JD 要求得满分，每低一档扣 30%
  赛道匹配   20%  简历实习/项目所属细分与 JD 细分的分类树相似度（同叶 1.0 → 同级 0.7 → 跨职能 0.2）
  证书匹配   10%  命中 JD 要求证书（如有）

sim_score = TF-IDF 余弦 × 100（升级后：与向量相似度加权）
```

### 5.3 输出

- Top-5~10 岗位，每岗位附：**命中技能 / 缺失技能 / 匹配理由**（由结构化字段生成，无需 LLM）。
- 用户无明确方向时的兜底：直接推荐"我的简历适合什么岗位"→ 报告目标 = Top-1 岗位；用户也可从推荐列表自选岗位再评分。

## 6. 五维评分引擎（核心）

> 总原则：**确定性公式算分 + LLM 只输出证据**。LLM 从简历+JD 抽取结构化证据（动作词、工具、量化数字、角色词、证书、信号词……），公式把证据映射为分数。可解释、可回归、可校准。

### 6.0 证据抽取（一次 LLM 调用）

```
输入：parsed_resume + 目标 JD（结构化）
输出 JSON：
{
  "evidence": {
    "internships": [{"company","track","duration_months","depth_keywords":[],"has_output":bool,"industry_cognition_signals":[]}],
    "skills": [{"skill","jd_required":bool,"is_core":bool,"evidence_level":0..4,"context":""}],
    "projects": [{"name","role_keywords":[],"tools":[],"action_verbs":[],"quantified":bool,"quant_text":"","complexity_signals":[]}],
    "certs": [{"name","scarcity_hint"}],
    "learning": {"github_evidence":bool,"blogs":bool,"course_timeline":bool,"self_driven_projects":[]},
    "cross_domain": {"dual_degree":bool,"minor":bool,"related_to_jd":bool},
    "industry_cognition": {"signals":[],"judged_level":0..3}
  },
  "doubt_flags": ["量化数字合理性存疑", ...]
}
```

### 6.1 经验匹配度（25 分）

| 子项 | 分值 | 量化规则 |
|---|---|---|
| 实习相关度 | 10 | 实习细分赛道与目标岗位赛道的分类树相似度 × 10（同叶 1.0 / 同职能 0.6 / 跨职能 0.2）；无实习 0 |
| 实践深度 | 9 | 时长（≥6月 3 / ≥3月 2 / ≥1月 1）＋ 深度词（独立负责/主导/从0到1/核心 3；参与/协助/跟进 1；无 0）＋ 有产出描述 3 |
| 行业认知 | 6 | LLM 判定 0~3（基于竞品分析/行业报告/用户洞察/政策解读等论述质量）＋ 信号词命中 0~3（行业报告、竞品分析、市场调研、用户画像、行业术语密度…） |

> 落地建议 ①（行业认知难量化）的处理：不看实习时长长短，而看**赛道对位 + 认知信号**；信号词表存配置表，可随校准反馈增量。

### 6.2 技能匹配度（25 分）

| 子项 | 分值 | 量化规则 |
|---|---|---|
| JD 技能覆盖率 | 10 | 核心技能（JD 中技能，按出现位置/频次/「必须/熟练」措辞分核心与加分）覆盖率 × 10；加分技能额外奖励，封顶 +2 |
| 熟练度（分层证据） | 9 | 见下表；核心技能取证据层均值，乘以 9 |
| 工具链完整度 | 6 | 岗位类别 `toolchain_template` 覆盖比例 × 6（如数据分析：Python/SQL/Excel/BI/统计方法） |

**熟练度分层证据模型**（落地建议 ② 的"分层测试逻辑"，从简历项目描述推断，杜绝"精通 Python"关键词陷阱）：

| 层级 | 含义 | 证据样例（来自简历描述） |
|---|---|---|
| L0 | 仅罗列无上下文 | 技能栏单写"Python" |
| L1 | 课程/认证/练习 | "《Python 数据分析》课程项目" |
| L2 | 项目中使用（基础层：调用库） | "用 pandas 处理数据并出图" |
| L3 | 独立开发工具/实现原理（进阶层） | "自研爬虫调度工具 / 实现 LRU 缓存" |
| L4 | 生产级/开源贡献/教学输出 | "开源项目 200+ star / 线上服务日调用 10 万次" |

> 实现要点：LLM 对每个技能标注 `evidence_level` 并给出上下文原文；无任何上下文支撑的技能证据层按 L0 计（防"精通=0 证据"刷分）。

### 6.3 项目质量（25 分，区分度核心）

| 子项 | 分值 | 量化规则 |
|---|---|---|
| 项目复杂度 | 9 | 复杂度信号：数据规模（万级+2/十万级+3/百万级+4）、技术深度词（算法/架构/性能优化/分布式…，每项+1）、技术名词数量（≥5 个 +2） |
| 个人角色 | 9 | **核心贡献者识别**：主导/独立负责/设计/搭建/从0到1（9 分档）；参与/协助/辅助（4 分档）；仅提及（1 分档）。取项目平均 |
| 成果量化 | 7 | **"动作-工具-量化结果"三元组**：完整三元组（"用 Python 处理 10 万条数据，效率提升 20%"）7 分；有量化无基准 3 分；无量化 0 分；量化合理性存疑（LLM `doubt_flags`）降一档 |

> 落地建议 ③ 的处理：LLM 证据抽取强制输出 `action_verbs / tools / quantified / quant_text`，公式检查三元组齐备性；`doubt_flags` 供人工复核（也进校准闭环）。

### 6.4 差异化竞争力（15 分）

| 子项 | 分值 | 量化规则 |
|---|---|---|
| 稀缺技能/证书 | 6 | 证书按 `cert_scarcity` 表取稀缺度分（1-5），命中最高者折算（≤6 分）；技能稀缺度 = 该技能在岗位库出现频率的逆频率归一化（≤2 分） |
| 跨领域背景 | 5 | 双学位/辅修/跨专业经历 3 分，且与目标岗位相关 +2 |
| 可量化成果 | 4 | 独立量化成果条数（≥3 条 4 / 2 条 3 / 1 条 2 / 0 条 0） |

**证书稀缺度表（初始值，待评审确认，样例）**：

| 稀缺度 | 示例 | 分值 |
|---|---|---|
| S | CPA、CFA 三级、FRM 二级、精算师 | 5 |
| A | CFA 一级、FRM 一级、ACCA、法律职业资格 | 4 |
| B | 软考中高级、PMP、二级口译 | 3 |
| C | 四六级、计算机二级、普通话 | 1 |

> 落地建议 ④ 前半的处理：区分"CFA 一级"与"FRM 二级"的含金量，用表驱动而非关键词堆砌；表存库、可随市场反馈调整。

### 6.5 成长潜力（10 分，AI 最难维度）

| 子项 | 分值 | 量化规则 |
|---|---|---|
| 学习轨迹 | 4 | GitHub 持续提交（主页链接+近 3 月活跃 2 / 有主页 1）、技术博客/专栏（1）、课程证书时间线连续（1） |
| 自我驱动 | 3 | 自发项目/开源参与/竞赛获奖/个人作品（每类 1 分，封顶 3） |
| 可塑性 | 3 | 跨领域学习信号（理工科辅修经管双学位类，1.5）＋ 复盘/自我驱动叙事词（"自学""复盘""主动""连续学习"，1.5） |

> 落地建议 ④ 后半的处理：**用侧面信号捕捉而非直接判断**——学习轨迹看"持续提交/博客/课程时间线"，可塑性看"跨领域实践 + 成长叙事"，全部来自证据抽取而非 LLM 自由发挥。

### 6.6 权重档位与总分（落地建议：分数段策略）

| 档位 | 经验 | 技能 | 项目 | 差异化 | 成长 | 适用场景 |
|---|---|---|---|---|---|---|
| 默认（综合） | 25 | 25 | 25 | 15 | 10 | 未明确目标时 |
| 大厂/高竞争 | 20 | 20 | 25 | **25** | 10 | 互联网大厂、量化、投行前台等：差异化决定前 10% |
| 国企/传统行业 | **30** | 20 | 15 | 5 | **20** | 国企、银行、传统行业：重成长潜力与稳定性 |

- **总分** = Σ(维度分 × 档位权重/100)，0~100。
- **档位触发**：系统按推荐岗位的公司类型/行业标签**自动建议**档位，用户可覆盖（下拉切换即时重算）。
- **等级映射**（初始建议，**待评审**）：≥85 S 强烈推荐 / ≥70 A 推荐 / ≥55 B 待定 / <55 C 需补强。
  > 注意：应届生整体分数分布未知，等级阈值可能在标注 50-100 份样本后回调整定（见 §8 冷启动）。
- **稳定性信号**（国企档附加）：不新增维度，作为经验匹配度的附加项（党员/学生干部/长期志愿服务等，+2 封顶），避免拆维度导致权重漂移。

## 7. 报告生成

- 复用 DeepSeek `generate_report`，输入五维分数 + 证据 + 档位，输出 Markdown 报告，结构固定：
  1. 总分 + 等级 + 档位说明
  2. 五维雷达数据（前端 ECharts 复用现有 `RadarChart.vue`）
  3. 逐维诊断：得分、证据、**差距项**（缺失技能/无量化/赛道不对位）
  4. **补强建议**（按差距项生成，如"补充 XX 技能的项目证据""为项目补量化结果"）
  5. 岗位匹配明细（命中/缺失技能 + 匹配理由）
- 报告与 `score_result` 结构保持 JSONB，兼容现有 `MatchReport`（维度从四维扩为五维，`version` 字段标记评分模型版本）。

## 8. 校准机制（落地建议：HR 反馈按钮）

### 8.1 反馈入口

- **C 端**（求职者）：报告页"这个评分准吗"——维度级（高估/低估/准确）+ 文本。
- **B 端**（HR，更可信）：报告页新增「校准反馈」——逐维「高估/低估/准确」+ 是否建议进入面试/录用 + 文本备注。HR 的录用/筛序行为是最高价值信号。

### 8.2 数据模型

```
calibration_feedback:
  id, analysis_id(FK), tenant_id, user_role(hr/candidate), jd_id(FK)
  dim_overrated(jsonb: 维度名[]), dim_underrated(jsonb), dim_ok(jsonb)
  agree_interview(bool null), comment(text)
  created_at
```

### 8.3 回流闭环（按周）

1. **统计**：每周聚合各维度"低估率/高估率"，输出校准看板（按档位、岗位类别、学校层次分组）。
2. **规则调参**（低风险，人工审核后生效）：信号词表增量、证书稀缺度调整、分层证据样例补充、等级阈值回调。
3. **提示词版本化**：评分 prompt 的 few-shot 参考样本从高质量反馈中挑选，每次改动打 `prompt_version`，全部随 `score_result` 落库可追溯。
4. **长期（反馈积累后）**：反馈 → 打分模型微调（LLM 打分蒸馏），用评估集回归，达标才上线。

### 8.4 评估指标

| 指标 | 定义 |
|---|---|
| 校准 MAE | \|模型分 − HR 认可分\| 的均值（HR 认可分 = 反馈修正后分值） |
| Top-K 命中率 | HR 确认录用/进入面试的简历在系统高分段的占比 |
| 维度偏差率 | 各维度被标"高估/低估"的比例（越低越好，>20% 触发调参） |
| 反馈采纳率 | 调参后评估集偏差下降的比例 |

### 8.5 冷启动

- 无反馈阶段：评分以**确定性规则为主**（LLM 只做证据抽取），保证规则透明、可解释。
- 上线前人工标注 50~100 份（简历 × 岗位）真值，作为评估集与等级阈值标定依据；HR 反馈开始积累后进入周度回流。

## 9. 技术选型（增量）

| 层 | 选型 | 说明 |
|---|---|---|
| 匹配 | scikit-learn `TfidfVectorizer` + jieba（加载技能本体词典） | 粗筛零成本；向量检索（sentence-transformers / bge-small-zh）M7.4 升级 |
| 结构化输出 | DeepSeek `response_format=json_object` | 解析 + 证据抽取共用，一次调用产出全维度证据 |
| 向量存储（可选） | pgvector（PostgreSQL 扩展） | M7.4 精排升级用，避免引入新中间件 |
| 配置表 | 信号词表/证书表/工具链模板/权重档位 → 数据库表 + 缓存 | 支撑校准闭环在线调参 |
| 前端 | Vue3 + Element Plus + ECharts（复用） | 新增 C 端路由与页面；雷达图组件复用 |
| 任务 | Celery（复用） | 岗位库清洗入库、批量推荐预筛（异步） |

**成本控制**：推荐流水线本地零 LLM 成本；五维评分每份简历一次 LLM 调用（证据抽取）+ 一次报告调用；Top-1~3 岗位共享同一次证据抽取。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 岗位库数据合规（平台条款/版权） | P0 人工种子 + P1 投稿起步；爬虫需法务评估，全程标注来源、可下架 |
| 应届生样本少、等级阈值不准 | 冷启动确定性规则 + 50~100 份人工标注标定；阈值存配置可回调 |
| "精通 Python"关键词陷阱 | 分层证据模型（L0-L4），无上下文证据按 L0 计 |
| LLM 打分不稳定/幻觉 | 确定性公式算分，LLM 只出证据；`doubt_flags` 供人工复核 |
| 校准反馈稀疏、偏差大 | 权重/阈值/信号词增量调整先行（人工审核），微调后置（评估集回归达标才上线） |
| 简历隐私 | 复用现有隔离/脱敏/删除策略；原件加密，推荐只留解析结果 |
| 评分维度扩展影响 B 端报告 | `score_result` 加 `version` 字段，B 端旧报告兼容显示 |

## 12. 待评审确认事项（编码前必须拍板）

| 评估集 | `app/models.py` `evaluation_case` | 简历×岗位 → HR 认可总分/等级（唯一约束防重复标注） |
| 标定 API | `app/api/routes/calibration.py` | `POST|GET|DELETE /eval-cases`、`GET /eval-report`（MAE + S80-89/A65-75/B50-60 全组合阈值扫描寻优）、`GET /training-data`（feedback + eval → JSONL 蒸馏数据集） |
| 前端 | `apps/web/src/pages/Calibration.vue` / `Candidate.vue` | 校准看板新增「评估集与阈值标定」（简历/岗位选择、标注表、标定报告、一键应用最优阈值）+「训练数据导出」；求职助手新增「收录岗位」对话框（分类树下拉） |

**实测结果**

- **向量精排生效**：模型经 hf-mirror 下载至 `.tools/hf-cache`（5 文件，首载约 5 分钟，之后命中缓存）；数据分析简历 Top-5 分数整体抬升（58.3→64.9 等）且排序微调（风控岗升到第 2）；Java 简历 Top-1 61.2→67.7；`VECTOR_RERANK_ENABLED=false` 或模型缺失时自动回退 TF-IDF（曾用下载失败验证回退路径，结果与纯 TF-IDF 完全一致）；
- **投稿**：提交「新媒体运营实习生」→ 自动归入 新媒体运营 分类、扫描出 4 项技能，岗位库 70→71；
- **评估标定**：1 条标注（模型 69 vs 认可 75，MAE=6.0）→ 阈值扫描给出最优 S80/A65/B50（准确率 1.0 vs 当前 0.0），可一键应用（复用 `PUT /settings` level_thresholds）；
- **训练数据**：feedback（含认可分）+ eval 标注 → 2 条 JSONL 结构化样本（resume_parsed + jd_text + 输出分数），供 LoRA 打分蒸馏。

**落地偏差与后续**

1. 向量精排用 fastembed/bge-small-zh（ONNX，免 GPU/torch），非方案中的 pgvector 检索；当前是"编码+余弦"，语料过万后再切 pgvector 向量索引（接口不变）；
2. 合规爬虫（P3）未实现——仅提供投稿入口与来源标注机制，爬虫需法务评估后另行实施（docs/07-§4.3）；
3. 打分蒸馏（LoRA SFT）未执行——数据管线就绪，标注/反馈积累 ≥200 条后按 docs/07-§8.3 长期路径执行；
4. 评估集标定样本少（1 条）仅验证链路，正式标定需 50-100 条人工标注。

## 17. 社招 JD 模式 vs 校招方向模式（M7.5，已落地实测）

### 17.1 为什么区分

- **社招**：岗位有明确 JD（职责/技能/年限具体）→ 简历 vs 单条 JD 的逐项对齐（现有能力）。
- **校招**：统招批次/提前批/管培往往**没有明确 JD**，只有"技术岗/产品岗/数据分析"等**方向**，
  甚至应届生自己也不知道投什么 → 需要"简历 vs 方向画像"的分析模式。

### 17.2 两种模式对照

| 维度 | JD 模式（社招/明确 JD） | 方向模式（校招/无 JD） |
|---|---|---|
| 分析目标 | 单条 JD | 方向画像（岗位族聚合） |
| 匹配对象 | JD 的结构化技能/职责 | 方向核心技能集 + 工具链 |
| 技能匹配度 | JD 技能覆盖率 | **方向核心技能覆盖率**（画像替代 JD） |
| 经验匹配度 | 年限/JD 要求 | 实习赛道对位方向（无年限要求） |
| 项目/差异化/成长 | 不变 | **原样复用**（本就不依赖 JD） |
| 入口 | 「开始岗位匹配」 | 「方向匹配（没有明确 JD）」 |
| 校准反馈 | ✅ 接校准闭环 | ❌ 暂不接（评分对象是方向，非单 JD） |

### 17.3 实现

| 模块 | 位置 | 说明 |
|---|---|---|
| 方向画像 | `app/services/jobmatch/direction.py` | 按 `jd_category` 叶子聚合岗位库 JD 技能频次（Top-12）+ `toolchain_template` 人工校验；岗位库扩充自动更新 |
| 方向匹配 | 同上 | 零 LLM：技能覆盖 50% + 赛道对位 30%（复用 track_sim）+ 工具链覆盖 20% + **专业对口加分 8 分**（`MAJOR_DIRECTION_MAP` 专业→就业方向先验，简历信息少时专业是最可靠方向信号，reason 标注"专业对口（XX专业 适配此方向）"） |
| 方向评分 | `app/api/routes/candidate.py` | `POST /candidate/direction-match`（方向推荐 Top-N）、`POST /candidate/direction-score`（方向级五维报告：方向画像构造**伪 JD**，evidence/scoring/report 全链路复用，`ScoreOut.mode=direction`） |
| 前端 | `apps/web/src/pages/Candidate.vue` | 上传后两按钮：「开始岗位匹配（有明确 JD）」/「方向匹配（没有明确 JD）」；方向卡片表 + 方向报告（隐藏校准反馈、档位重算走 direction-score） |

### 17.4 实测

- 数据分析应届生（统计学专业）→ **数据分析方向 99.7 分**（专业对口 +8；命中 SQL/Python/Excel/Tableau/A-B测试 等 10 项），
  算法 63.5（专业映射也覆盖算法方向）、测试 51.0 / 新媒体 33.9（跨职能正确降分）；
- Java 后端应届生 → **后端开发方向 92.9 分**（命中 12 项），测试 76.0 / 运维 52.4；
- 运营简历（市场营销专业）→ 用户运营 92.9 / 电商运营 83.9（专业+技能双重命中）；
- 方向级五维报告：数据分析方向 67.3 分（与同类别 JD 模式 67.0 一致，验证画像聚合忠实于岗位库）。

## 18. 求职助手两模块 + 校招简历优化分析（M7.6，已落地实测）

### 18.1 页面结构（按求职场景拆模块）

求职助手（`/candidate`）拆为两个 tab，避免"社招岗位匹配"与 B 端批量分析重复建设：

| Tab | 定位 | 能力 | 与已有功能的复用关系 |
|---|---|---|---|
| **社招求职**（有明确 JD） | 求职者视角的单份简历×岗位匹配 | 岗位推荐（命中/缺失技能）+ 五维报告 + 校准反馈 + 收录岗位 | 与批量分析（HR 视角）**共享同一引擎**（推荐/评分/反馈），仅入口与视角不同，不重复实现 |
| **校招求职**（无明确 JD） | 应届生没有明确 JD 的场景 | ① 方向匹配（方向画像）② 方向级五维报告 ③ **简历优化分析（新增）** | ①②复用 M7.5；③为新增的纯简历侧诊断 |

### 18.2 校招简历优化分析（新增核心能力）

纯简历侧诊断，**不依赖任何 JD**，一次 LLM 调用输出结构化优化建议：

```
简历 → DeepSeek 解析 → 优化分析 LLM
  → ① completeness 完整性逐项检查（教育/GPA/实习产出/项目量化/技能证据/证书/自我评价/主页/联系方式）
  → ② dimension_suggestions 按五维的可执行改写建议
  → ③ quick_wins 高性价比改动（按成本排序）
  → ④ example_lines "动作-工具-量化"参考写法（结合该简历实际经历改写）
  → ⑤ risk_flags 风险点（空档/夸大/矛盾）
```

| 模块 | 位置 | 说明 |
|---|---|---|
| 分析服务 | `app/services/jobmatch/resume_analyze.py` | LLM 结构化诊断；无 LLM 时 `fallback_analysis` 规则兜底 |
| API | `POST /candidate/resume-analysis` | 上传简历 → 解析 → 优化建议 JSON |
| 前端 | `apps/web/src/pages/CandidateCampus.vue` | 校招 tab：方向匹配 + 「简历分析 + 优化建议」按钮与展示（完整性表格/五维折叠建议/参考写法/风险） |

### 18.3 实测

- 数据分析应届生简历 → 完整性 9 项中 8 项达标、1 项待补（缺 GitHub/博客链接）；
  项目质量建议具体到条目：如"将'使用Tableau制作看板'改为'独立设计并开发Tableau看板，推动运营策略调整'"，并提示补充样本量与业务落地效果；
- 前端拆分后：社招 tab（岗位匹配+报告+反馈）与校招 tab（方向匹配+优化建议）各自独立状态，互不干扰；
- 方向匹配/五维评分回归不受影响（Java 简历 → 后端方向 92.9 分）。

### 18.4 通用 vs 针对性优化建议（M7.9，已落地）

产品决策：**分层策略——通用版保底 + 针对性进阶**，两者都保留：

| 场景 | 模式 | 说明 |
|---|---|---|
| 应届生不知道自己能做什么 | **通用版**（默认） | 纯简历侧诊断（完整性 + 五维建议），配合方向匹配推荐方向 |

  把版面让给相关经历，突出针对性；实测：数据分析简历 → 两段数据分析实习与流失预测项目"详写"

## 20. 岗位库 JD 抓取（crawl4ai，P3 合规爬虫，已落地实测）

### 20.1 背景

docs/07-§4.3 预留的 P3 合规爬虫已落地：安装 crawl4ai skill 并实现岗位库抓取脚本，
把公开招聘页的岗位 JD 抓入 `jd_library`（技能/证书本地扫描 + 分类映射 + 来源标注）。

### 20.2 环境（沙箱友好，均已装好）

```dotenv
# .tools/crawl4ai       crawl4ai 数据目录（CRAWL4_AI_BASE_DIRECTORY）
# .tools/pw-browsers    Playwright chromium 内核（PLAYWRIGHT_BROWSERS_PATH）
pip install crawl4ai
python -m playwright install chromium   # 国内用 PLAYWRIGHT_DOWNLOAD_HOST=https://npmmirror.com/mirrors/playwright
```

### 20.3 用法

```bash
cd apps/api
python scripts/crawl_jobs.py --mode lever --url https://jobs.lever.co/leverdemo --limit 10 --delay 1.5
# 通用列表页（CSS schema 或 Markdown 正则回退）：
python scripts/crawl_jobs.py --url https://example.com/jobs --category 后端开发 --industry 互联网
```

流程：列表页（JsonCssExtractionStrategy schema / Markdown `[标题](uuid链接)` 正则回退）
→ 详情页（css_selector 提取 JD 正文，≤6000 字）→ 入库（技能/证书扫描生成 `jd_parsed`、
标题关键词自动映射职能叶子、`source=crawler` + `source_url` 可溯源下架）。

### 20.4 实测

- Lever ATS demo（`jobs.lever.co/leverdemo`，服务端渲染、公开数据）：列表 100+ 岗位 → 详情 → 入库；
  英文岗位标题自动映射中文职能叶子（Account Executive→市场营销、Data Analyst→数据分析、
  Software Engineer→后端开发 等），入库岗位**自动参与求职助手**：
  - 岗位库可检索（`GET /candidate/jd-library`，source=crawler 带"抓取"来源）；
  - **方向画像自动聚合**（实测：市场营销方向 5 种子 + 6 抓取 = 11 条样本）；
  - **简历推荐候选池参与**（TF-IDF 粗筛包含，按相关性精排；Lever 样例为英文销售岗，与中文
    技术简历相关性低属内容问题——抓中文岗位源后直接生效）；
- 合规内置：`cache_mode` 禁用防陈旧 + 详情请求间隔 `--delay` + 来源标注 + 仅公开内容。

### 20.5 求职助手联动（M7.8）

```
求职助手「扩充岗位库」→ POST /api/v1/candidate/jd/crawl（urls/mode/limit）
  → crawl4ai 抓列表+详情 → 英文→中文分类映射 → jd_library 入库
  → 求职助手「岗位匹配」与「方向匹配」自动覆盖新岗位（无需改代码）
```

- 前端入口：社招求职 tab 头部「扩充岗位库」按钮（URL 多行 + 站点适配 + 数量上限），
  推荐列表岗位带来源标签（抓取/投稿）；
- 核心逻辑抽到 `app/services/jobmatch/crawler.py`（CLI `scripts/crawl_jobs.py` 与 API 共用）；
- **沙箱限制**：playwright 启动浏览器需进程管道，本沙箱内 API 调用返回带命令行指引的降级提示
  （502），CLI 需放开权限运行；生产环境（Docker/真机）无此限制，API 可直接抓取。

### 20.6 合规与扩展

1. **合规**：仅抓公开可见内容；遵守目标站点 robots/条款；控制频率；`source_url` 可溯源，收到删除请求即下架（`is_active=false`）；
2. **SSRF 防护（代码审查加固）**：`crawler.py` 对列表页 URL、详情页 URL（相对路径先 `urljoin`）做三重校验——
   仅允许 http/https 协议；DNS 解析后拒绝私网/环回/链路本地/保留地址（`127/8`、`10/8`、`172.16/12`、`192.168/16`、
   `169.254/16`、`::1`、`fc00::/7` 等）；跟随重定向后的最终地址同样复检。`POST /jd/crawl` 路由先逐条预校验，
   任一 URL 不合法直接 400；`crawl_and_save` 内部对不安全 URL 跳过并计入 failed（纵深防御）。
3. **扩展**：新站点三步接入——探测页面结构 → 写 schema 或加 `--mode` 内置适配 → 复用入库逻辑；
   岗位库扩充后「方向画像」自动更新（M7.5）；
4. 英文→中文映射表（`crawler.EN_TITLE_MAP`）可随业务扩充关键词；
5. **抓取去重**：`save_to_library` 按 `(source='crawler', source_url)` 查重，命中则更新
   `jd_text/jd_parsed/crawl_at` 而非新增，重复抓取同一列表页不会产生重复岗位。

| 极客技术 tech | 技术岗 | 深色顶栏 + 等宽字体（monospace）+ 绿色 accent + 技术标签 chips |

### 19.2 流程与实现

```
简历 → DeepSeek 解析 → 优化分析（resume_analyze）→ LLM 改写（resume_rewrite）
  → 结构化内容 JSON（personal/education/summary/internships/projects(动作-工具-量化)/
     skills 分组/certs/achievements/still_to_add）
  → 前端 4 风格模板渲染（ResumePreview.vue，A4 画布 + 字体栈 + 首字母头像占位）
  → 「打印 / 导出 PDF」（window.print + @media print 仅输出简历画布）
```

- 后端：`app/services/jobmatch/resume_rewrite.py` + `POST /candidate/resume-rewrite`
- 前端：`apps/web/src/components/ResumePreview.vue`（4 套模板）+ 校招 tab 集成
- **忠实性约束**：只强化表达（动作-工具-量化），不虚构经历/数据/证书；原文缺失的高价值内容
  写入 `still_to_add` 由用户手动补充（前端醒目标注），避免把占位写进正文

### 19.3 实测

- 数据分析应届生 → 求职意向"数据分析师"；实习改写为"使用 SQL 从订单表提取 50 万条数据，输出活动复盘报告"；
  项目带技术标签（Python/pandas/scikit-learn/Tableau）与量化（AUC 0.82）；
  still_to_add 5 条（GitHub 主页、专业排名、PowerBI 应用场景、项目数据规模、数据分析证书）；
- Java 应届生 → 求职意向"Java后端开发工程师"，技能 5 组，项目 2 个，同样生成 4 风格预览可打印。

### 23.2 实现

| 模块 | 位置 | 说明 |
|---|---|---|

### 23.3 实测

- 合成中文简历截图（PIL 绘制）OCR：姓名/电话/教育/实习/技能行全部命中；
- 图片型 PDF（整页无文本层）渲染 OCR：内容完整识别（含教育经历行）；
- 端到端：上传 png 简历 → 推荐接口 200，命中技能 Excel/Python/SQL/数据可视化 与图内技能行一致；
- 性能：单页 CPU 识别 ~9s；扫描件多页耗时线性增加（≤6 页上限，避免拖垮）。

## 24. 求稳赛道岗位库（银行/央国企，M7.13）

### 24.1 背景

应届生就业偏好显著向"求稳"倾斜：银行（柜员/客户经理/运营支持/管培）与央国企（电网/运营商/
建筑/能源通用岗）是规模最大的校招出口。银行岗现实存在「网申 → 笔试（行测+经济金融）→ 面试」的
考试制流程，此前岗位库未覆盖，金融/会计/经管类简历匹配不到对口岗位。

### 24.2 实现

| 模块 | 说明 |
|---|---|
| 分类树 | `FUNCTION_TREE` 新增一级职能「金融综合」：综合柜员/客户经理助理/运营支持/管理培训生 4 个叶子 |
| 种子 JD | `JD_SEEDS` 追加 14 条求稳岗位（银行 8 + 央国企 6，真实校招文案），行业归既有「金融/互联网/制造业/专业服务」 |
| 岗位标签 | `jd_parsed.meta` 存 `stability(bank/soe)`、`selection(exam/direct/mixed)`、`exam_note`（流程提示）、`tags`——不改表结构，随自由 JSON |
| 幂等增量 | `ensure_stability_seed`：老库无需 force，仅补缺失分类叶子与求稳岗位（title+company 去重），不动用户/爬虫数据 |
| 序列化 | `_jd_item`/`JdLibraryItem` 带出 stability/selection/exam_note/jd_tags（推荐/列表/详情/校准选择全局生效） |
| 方向映射 | `MAJOR_DIRECTION_MAP`：经济/金融/保险/投资 → 客户经理助理/综合柜员/运营支持/财务/市场营销；会计 → 财务/综合柜员；工商管理/国贸 → 加客户经理助理 |
| 前端 | 推荐列表岗位标题加「🏦 银行 / 🏢 央国企」标签；考试制岗位在 meta 行展示 📌 笔试流程提示（浅黄底） |

### 24.3 实测

- 老库 85 → 99 条（+14，幂等两次请求均为 99）；
- 分类接口出现「金融综合」一级（技术/产品/运营/市场/职能/金融综合）；
- 金融学简历方向匹配 Top3 = 综合柜员/客户经理助理/运营支持（专业对口 +8 生效）；
- 金融简历推荐 Top3 均为 `bank/exam` 岗，推荐卡片携带「网申→笔试→面试」exam_note 提示；
- 合规口径：标签如实标注"需参加校招笔试"，匹配分仅代表简历适配度，不承诺录取。

### 24.4 方向匹配低门槛校准（配合 M7.13 上线后修正）

- **问题**：柜员/客服/行政等方向技能集窄（<6 项），命中一两项即接近 100% 覆盖率 → 分数虚高
  （"要求低 = 分高"失真），技能稀疏简历被系统性推向低门槛岗；
- **修复**：`direction_match_score` 覆盖率分母按下限 6 校准（`MIN_SKILL_SCOPE`），
  低门槛方向分数回归理性；新增 `skill_scope`/`low_barrier` 字段供前端标注；
- **前端**：方向卡片对 `low_barrier=true` 的方向显示「低门槛·分易偏高」标签 + tooltip 解释；
  reason 同步追加"门槛较低，命中分偏高不代表竞争小"说明；
- **实测**：同一份"银行柜员意向"简历，综合柜员分数校准下降但仍第一（其简历文本确属柜员定向，
  结果合理）；纯技术简历不受影响（技能集 ≥6 不触发补偿）。

## 26. 求职导航（问卷 → 画像 → 差距 → 行动路线图，M7.15）

### 26.1 背景

产品原从"简历匹配"开始，学生没有简历（经历空白）时无处下手。将入口**前移**到求职导航（原名"职业规划"，命名偏重已弃用）：
无简历也能用问卷勾勒画像、选定目标岗位方向、找出差距并给出补足路线（实习/技能/证书/比赛）。

### 26.2 流程与实现

```
① 问卷(单页分区) → ② 画像 → ③ 选目标(岗位库方向) → ④ 差距矩阵 → ⑤ 行动路线图+比赛/证书清单
```

| 模块 | 说明 |
|---|---|
| 知识资产 | `career_assets.py`：22 个方向 → 8 个岗位族（tech/data/product/content_op/marketing/func_hr/…/bank/general），每族含 技能补足路径 / 建议证书 / **含金量比赛清单**(名称·主办·★·难度·时机) / 替代经历 / 实习建议；免责声明（认证备案、防山寨） |
| 画像与差距 | `career_plan.py` 确定性规则：画像摘要 6 行（基本盘/时间/经历资产/特质偏好/已备技能/目标）；差距按 实习相关度·技能覆盖·证书·比赛项目 判断（无 LLM 也能跑） |
| 路线图 | 按剩余学期分阶段：①知识+考证 ②比赛/替代经历 ③暑期实习 ④秋招冲刺；无实习→实习动作 high；剩余 ≤2 学期自动插"时间提醒" |
| 总评 | LLM 生成 220 字"画像定位 + 12 个月主轴"（失败降级规则文案，`overall_source` 标注来源） |
| API | `GET /direction-profile?name=`（方向核心技能/工具链，供勾选"已会技能"）；`POST /career-plan`（问卷 JSON） |
| 前端 | 求职助手**最左 tab「求职导航」**（默认打开）：单页分区表单（①基本信息 ②经历盘点 ③擅长[基础能力≠方向/可职业化特长] ④特质偏好 ⑤目标=想做的事：直接就业(方向或自动推荐)/考研(本跨)/考公考编(国省事) ⑥已会技能 chips，仅就业时显示）→ 结果卡（AI 总评/画像/差距/分阶段路线图/比赛与证书建议[仅就业]/免责） |

### 26.3 口径

- 目标岗位限**岗位库已有方向**（22 个叶子，数据可查），不开放自定义（避免 LLM 编造岗位要求）；
- **求职导航 v4（目标放第一位，按目标动态出题）**：
  - 第一题即"目标 = 想做的事"：**直接就业 / 考研 / 考公考编**，之后的题目只问与所选目标相关的字段
    （考研不问实习、不展示基础能力；考公不问 GPA/项目/竞赛；就业保留全套 + 已会技能 chips）；
  - **考研**：追问 本专业/跨考 + **预计考试时间**（明年12月/后年/更久/没定）；**考公/考编**：追问 国省事 + **报考窗口**（应届年/毕业后一年/没定）+ **政治面貌**（群众/积极分子/预备/正式）；
    引擎对考公给"先入党"优先建议（非党员→递交入党申请；积极分子→争取发展名额；预备/正式→确认材料可用于选调/党员限制岗）；
    引擎输出 `target_kind=grad/civil` 专线：画像+差距+分阶段路线（不再列岗位比赛/证书），并强调**备考开始时间因人而异、不套标准**——
    按"距考试月数 × 每周可投入"给出"最晚启动建议"（如每周5小时约需16个月→12个月才备考即提示立即开始并压缩基础期）；
  - 就业场景保留"可职业化特长→优势路线/自动推荐"、无强优势则选目标岗位以终为始；
  - 旧问卷调用（无 `target_kind`）默认按就业路径，完全兼容。
- "已会技能"用目标方向核心技能 chips 勾选（比自由文本可对比）；
- 问卷②"经历盘点"在 项目/竞赛数量 >0 时**补充采集具体内容**（名称｜技术栈/级别｜角色｜结果，可选填）：画像增加
  "项目/课设、竞赛获奖"明细行；差距按 项目×比赛×明细 细分（有项目无比赛 / 有比赛无项目 / 数量有但没写细节会提示补全）；
  路线图第二阶段据明细给出"打磨已有项目/竞赛成果为简历素材"动作；总评 LLM 亦可见该明细。
- 规划为参考、不承诺结果；比赛/证书以官方与主办方为准。

### 26.4 实测（HR 案例：大三/汉语言/零实习零项目零比赛 → 人力资源）
